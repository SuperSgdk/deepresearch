# 项目架构与请求流程

我将 DeepResearch 的处理过程划分为 API 接入、研究工作流、检索与记忆几个部分：FastAPI 接收请求，LangGraph 编排研究节点，网络搜索与本地知识库提供证据，记忆模块保存会话上下文。以下是当前实现中的一次请求流程。

1. 网页提交问题和用户、租户、会话标识到 FastAPI。
2. `WorkflowService` 加载配置，构建 Agent、记忆管理器和工作流。
3. 意图节点选择直接回答或多 Agent 研究。研究检索由 Python 执行，Agent 负责规划、证据整理、审查与写作。
4. 网络与本地检索并行完成后，证据审查节点再运行；分析节点判断信息缺口。
5. 有缺口且未达上限时，由独立的补搜角色生成新搜索词。`MAX_ITERATIONS=1` 表示初始研究后最多再补搜一次。
6. 写作节点接收当前证据与来源索引，删除无效来源编号，并按当前报告生成来源清单。
7. 后端保存本轮记忆，SSE 发送最终结果。

PostgreSQL 负责对话记录与工作流检查点；Milvus 负责知识片段与语义记忆检索。知识与记忆使用不同集合。Redis 是可选短期记忆后端，默认不启动。

网页的新聊天 ID 和后台复合检查点标识用于防止串会话；它们不提供身份认证。用户级长期记忆会跨聊天召回，完整隔离需使用不同用户标识。
